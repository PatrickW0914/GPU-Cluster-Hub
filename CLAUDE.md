## What the application is

GPU Cluster Hub manages a shared graduate-student GPU cluster:
- a catalog of AI models, their versions (checkpoints), and verified software environments,
- the hardware inventory (compute nodes, GPU types, GPUs) and which checkpoints are staged on which node,
- GPU reservations with conflict detection and weekly per-group GPU-hour quotas,
- jobs run inside reservations and the model versions each job loads.

Users: researchers (book GPUs, find models), PIs (manage group, quota, reports), admins (inventory, catalog).

## Schema summary (see sql/01_schema.sql for the truth)

Entities: `cluster_user`, `research_group`, `compute_node`, `gpu_type`, `gpu`, `ai_model`,
`model_version` (weak: PK (model_id, version_tag)), `software_env`, `reservation`, `job`.
M:N tables: `membership` (user↔group), `node_hosts_version`, `env_supports_version`,
`reservation_gpu`, `job_loads_version`.
Views: `v_reservation_hours` (gpu_count, gpu_hours per reservation), `v_gpu_inventory`.
Key design points:
- `research_group.pi_user_id` → membership (DEFERRABLE INITIALLY DEFERRED). Creating a group
  = insert group + PI membership in ONE transaction.
- `reservation (user_id, group_id)` → `membership`: users can only book for their own group.
- Identity columns are `GENERATED BY DEFAULT AS IDENTITY`; use `INSERT ... RETURNING id`.
- Timestamps are `TIMESTAMP` (cluster local time). Sample data is a snapshot at
  **2026-11-02 09:00**. The app must have a "current time" setting (default: that snapshot
  for demo; option: real now) and pass it as a parameter to time-dependent queries.

## Database error codes the app must translate into friendly messages

| SQLSTATE | Meaning | Example user message |
|---|---|---|
| 23505 | unique violation | "A user with that NetID already exists." |
| 23503 | foreign key violation | "Can't delete: this record is still referenced by …" / "Referenced record doesn't exist." |
| 23502 | not null violation | "Field X is required." |
| 23514 | check violation | name the constraint → readable rule (e.g. ck_res_maxlen → "Reservations can't exceed 72 hours.") |
| GH001 | GPU double-booked | "GPU N is already booked during that time." |
| GH002 | GPU not bookable | "That GPU is in maintenance/retired or its node isn't UP." |
| GH003 | weekly quota exceeded | "This booking would exceed your group's weekly GPU-hour quota." |
| GH004 | reservation with no GPU | "Select at least one GPU." |
| GH005 | job outside reservation window | "Job times must fall within the reservation." |
| GH006 | env not verified for model | "That model version isn't verified for this environment." |
| GH007 | node storage full | "Not enough NVMe space on that node." |
| GH008 | PI must be Faculty | "A group's PI must be a Faculty user." |
| 08xxx | connection failure | "Can't reach the database — check config/db.properties and that PostgreSQL is running." |

Put this mapping in ONE class (e.g. `db/SqlErrors.java`) and use it everywhere.
Show the trigger's own message text as detail (it is already human-readable).

**Deferred constraints fire at COMMIT**: GH004 and the group-PI FK can be thrown by
`connection.commit()`, not by the INSERT. Always wrap commit in the same try/catch and roll back.

## Transactions (required demo item)

"Book N GPUs" = one transaction: `setAutoCommit(false)` → INSERT reservation RETURNING id →
INSERT one `reservation_gpu` row per GPU → `commit()`; on any SQLException → `rollback()`,
restore autoCommit, show mapped message. Must demonstrate a failing booking leaving no rows.
Second transaction: create research group + PI membership together.

## Rules for working in this repo

- Do not change `sql/01_schema.sql` unless asked. If a change is truly needed, explain why
  first, then record it in `docs/SCHEMA_CHANGES.md` (what, why, date) — the course requires
  documenting schema changes. After any schema change, rerun the rebuild + constraint tests.
- Port queries from `sql/03_planned_queries.sql` faithfully; psql variables (`:'now'`, `:model`)
  become `?` parameters.
- Validate input in the GUI before hitting the DB (required fields, numbers, date order), AND
  still handle DB errors (the DB is the final authority).
- Never run destructive commands on databases other than `gpuhub`, `gpuhub_large`, or a
  throwaway test DB.
- Keep classes small: `db/` (connection, errors), `dao/` (one class per entity, SQL only),
  `service/` (transactions, slot finder), `ui/` (Swing panels). No SQL inside UI classes.
- After each milestone: build (`mvn -q package`), run the app or a smoke test, summarize what
  changed and how to demo it, and suggest a git commit message. Don't commit unless asked.
- Credit external libraries and AI assistance in the final report's references section
  (course policy: acknowledge external resources).
